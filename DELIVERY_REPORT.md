# Automated Certificate Renewal — Delivery Report

**To:** Engineering lead, Clear Ops / AI Control Plane
**Re:** Opt-in automated certificate renewal feature package (.NET 8 API + Next.js 14 web)

## Summary

This package adds automated SSL/TLS certificate renewal to Clear Ops as a standalone, integration-ready feature. The platform already raises Critical findings for expired and expiring certificates; this closes the loop by renewing them — but only for certificates a user has explicitly opted in, one at a time, with the enabling user and timestamp recorded. The backend is a .NET 8 solution of five projects plus a test project (builds clean, 81/81 xUnit tests passing), and the frontend is a typed Next.js 14 client component with a matching API client. Renewal method is selected per certificate: Key Vault certificates are re-issued through `Azure.Security.KeyVault.Certificates`, App Service managed certificates through `Azure.ResourceManager.AppService`, and external certificates from ACME CAs (Let's Encrypt/ZeroSSL) through the ACME protocol with DNS-01/HTTP-01 validation. Certificates that cannot be renewed automatically — paid-CA certs (GlobalSign, Sectigo, GoDaddy, etc.), imported Key Vault certs, uploaded App Service certs — instead produce a Work Item assigned to the certificate owner with issuer-specific renewal instructions.

## Safety

Nothing renews without an explicit, attributed opt-in: the gate is enforced inside the engine on every code path, so neither the background sweep, the API, nor the "run now" action can renew a certificate no one enabled. The package also ships with dry-run on by default — every attempt runs the full pipeline and writes an audit record describing exactly what a live run would do, while making no changes to Azure, DNS, or Work Items — and dry-run can additionally be pinned per tenant or per certificate. Tenant isolation is structural: all queries are tenant-filtered, the engine re-checks the certificate's tenant before each attempt, and Azure credentials are resolved from the certificate's own tenant. Every attempt is audited with status, timestamps, the new expiry and thumbprint on success, and the error on failure; after a live success the engine re-reads the resource from Azure to verify the new expiry before recording it. Failures retry up to three times with a six-hour cooldown, then escalate to an owner-assigned Work Item; Work Items and approvals are deduplicated per expiry cycle so repeated sweeps can never create duplicates. An optional approval mode holds each renewal until a user approves it in a queue, which is a useful stage between dry-run and fully automatic.

## Integration work required

Seven small interfaces connect the package to the existing product, each documented with examples in README_INTEGRATION.md: a repository mapping the existing certificates table to the engine's model (the table itself is not modified), the per-tenant Azure credential store already used by scan jobs, Work Item creation, three notification hooks, authentication/RBAC for the API endpoints, and a scheduler call — one method invoked after each tenant scan, or the included hourly background service. Persistence for the three new tables (policies, attempts, approvals) is provided as EF Core entities with repositories, or as a plain SQL migration (`dotnet/migrations/`). On the web side, `CertificateRenewalPanel.tsx` drops into the certificate detail view and `renewalApi.ts` provides a typed client for the nine REST endpoints (opt-in/out, settings, audit history, manual trigger, approvals). Example configuration is in `appsettings.example.json`; all settings can also come from environment variables.

## Verification status and rollout

The engine logic is fully tested: 81 xUnit tests cover opt-in enforcement, renewal-window math (expired certificates included), dry-run at all three levels, retry and escalation, cross-tenant rejection, the manual fallback, approvals, deduplication, and post-renewal verification. The three Azure/ACME providers compile against current SDK versions but have not been exercised against live Azure resources from this environment — the rollout plan is designed accordingly. Recommended sequence: deploy with defaults (dry-run on) and read the audit records; wire the real Work Item and notification integrations; optionally enable approval mode; then go live for a single pilot tenant with all other tenants pinned to dry-run and the per-sweep cap set low, starting with a self-signed Key Vault certificate; for ACME, use the Let's Encrypt staging directory before production. Required Azure permissions per tenant service principal: Key Vault Certificates Officer on target vaults, `Microsoft.Web/certificates` read/write on the resource group, and DNS Zone Contributor only if ACME DNS-01 via Azure DNS is used. One design decision is left to the team: where ACME-issued certificates get installed (`ICertificateInstaller`, e.g. Key Vault import) — until configured, ACME-eligible certificates safely fall back to Work Items. The bundled header-based auth resolver is a development placeholder and must be replaced with real authentication before the endpoints are exposed.
